# Аудит SQL Formatter — 14.10.2026

## Объём и ограничения
Изучен предоставленный `SQL_formatter_review.zip`: `formatter.py` (44 902 байта), адаптер DBeaver, 9 модулей `formatter_modules`, тесты, `.sqlfluff`, контракты v1/v1.1 и журналы. Это **статический аудит**: в среде проверки отсутствует `sqlfluff`, поэтому запуск проекта и динамическое подтверждение дефектов здесь не выполнялись. Журнал `docs/test_results.txt` находится в архиве, но может предшествовать последним ручным исправлениям. Со слов пользователя последний прогон до исправления CLI-пути: 85 тестов, 54 FAIL, 4 ERROR. Эти числа — исходная точка, не результат повторного запуска.

## Ключевой вывод
Форматтер находится в промежуточной архитектуре: часть правил делает позиционные AST-правки, часть заменяет целые клаузы, часть преобразует весь SQL после AST-этапа. Эти механизмы конкурируют за одни и те же участки, а `plan_edits()` пропускает конфликтующие правки. Прежде чем расширять набор правил, нужно восстановить наблюдаемость и единый контракт изменения исходного текста.

## Подтверждено исходным кодом

### P0 — пересечения правок могут приводить к частичному форматированию
- `formatter.py:965–1111`: `format_sql()` собирает правки из SELECT, FROM, JOIN, WHERE и других обработчиков, затем вызывает один `plan_edits()`.
- `formatter_modules/formatter_edits.py:33–55`: правки сортируются **по длине диапазона**, а при пересечении новая правка пропускается с `SQLFMT-E001`. Это не атомарная операция на уровне SQL-конструкции. При пересечении короткая правка может выиграть у более полной.
- `formatter_modules/formatter_list_gaps.py:11–69`: SELECT меняется по отдельным gap-диапазонам; `formatter_modules/formatter_clause_gaps.py:17–66`: другие клаузы иногда меняются целиком. При вложенных структурах вероятность пересечения повышается.
- Рекомендация: воспроизвести один минимальный случай с диагностикой диапазонов, после чего обеспечить явный приоритет/владение AST-участками и атомарное принятие логической группы правок. Не отключать предупреждения ради зелёных тестов.

### P0 — защита содержимого не равна гарантии семантики
- `formatter_modules/formatter_guarded_pass.py:12–41`: `SequenceMatcher` превращает результат глобальной текстовой трансформации в правки и фильтрует пересечения с защищёнными spans. Отдельные фрагменты одного преобразования могут быть приняты, другие отклонены, что потенциально оставляет промежуточный результат.
- `formatter.py:813–848`: `validate_sql_unchanged()` сравнивает токены SQLFluff и порядок комментариев; исключает некоторые токены `WHERE 1=1 AND` через `remove_formatter_where_prefix()`. Это полезная защита, но не доказательство эквивалентности запросов и не гарантия идемпотентности.
- Рекомендация: тесты на атомарность, сохранение байтов литералов/комментариев, повторное форматирование, корректность исключения `WHERE 1=1`.

### P1 — отсутствие надёжного формирования границ клауз
- `formatter.py:574–699` (`format_clause_spacing`) работает только с **началом строк**: регулярное выражение сопоставляет `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `JOIN` после отступов. Функция не разбивает `... FROM ... WHERE ...` внутри одной строки и не включает `FROM` в список ключевых слов.
- `formatter_modules/formatter_clause_gaps.py:17–66` для `from_clause` форматирует внутренности FROM, но не вставляет границу **перед** FROM. При наличии JOIN или вложенного запроса отказывается от правки.
- Следствие: показанные ранее результаты вроде `id FROM users` совместимы с этой конструкцией; это **сильная гипотеза корневой причины**, требующая трассировки AST-границ.
- Рекомендация: AST-anchored вставки/замены **пробелов между соседними клаузами** с учётом комментариев и вложенности, а не regex-разрезание SQL.

### P1 — правила не полностью согласованы с контрактом
- `formatter.py:500–571` (`format_where_clause`) вставляет `WHERE 1=1` при обнаружении AND; `docs/contract_bochenkov.md` требует это для нескольких AND-условий в WHERE/HAVING. При этом HAVING отдельным аналогичным обработчиком не охвачен в `format_sql()`.
- `formatter.py:574–699` нормализует существующие пустые строки, но не гарантирует добавление одной пустой строки, если её не было: проверьте договорённости в `docs/teradata_formatter_contract_v1.1.md` и golden-тесты.
- `formatter_modules/formatter_clause_gaps.py` для одиночного GROUP/ORDER оставляет одну строку; для сложных выражений, комментариев и JOIN консервативно отступает. Это осознанное ограничение, но создаёт неполное форматирование.
- Рекомендация: формализовать матрицу «обязательное форматирование / безопасный отказ + диагностика» на основе v1.1, не переписывать контракт под текущий вывод.

### P1 — возможная неидемпотентность и конфликт этапов
- `formatter.py:965–1111`: `normalize_groupby_header_comments()` вызывается до парсинга, далее AST-правки, затем последовательно `clean_blank_line_whitespace`, `format_clause_spacing`, `format_semicolons`, `normalize_select_field_indents`, `remove_select_blank_lines` через `guarded_pass()`.
- Несколько этапов изменяют отступы/пустые строки; не показано, что порядок стабилен на втором проходе. Нужны адресные тесты `format_sql(format_sql(x)) == format_sql(x)` с записью промежуточных состояний.

### P1 — CLI и окружение
- `formatter.py:5`: `sys.stdout.reconfigure(encoding='utf-8')` вызывается при импорте, что меняет глобальный stdout и может не работать в окружениях без `reconfigure`. Перенести конфигурацию вывода в CLI-путь, сохранив UTF-8 DBeaver.
- `dbeaver_formatter.py` импортирует `format_sql` и пишет `result.encode('utf-8')` в `sys.stdout.buffer`; ошибки ограничены `(OSError, UnicodeError, ValueError)`. Нужен smoke-test subprocess, stdout только SQL, stderr только диагностика.
- `tests/contract/test_contract_edge_v1_2.py:186` в архиве уже использует `Path(__file__).resolve().parents[2] / 'formatter.py'`; проверить после перемещения.

### P2 — структура и тестовый долг
- В `tests/regression` есть несколько близких копий `test_formatter*.py`, отчего количество падений дублируется. Сначала сравнить хеши/различия и сохранить уникальные сценарии, затем аккуратно устранить дубли.
- `formatter_modules/formatter_comment_lists.py`, `_v2.py`, `_v3.py` сосуществуют; основной `formatter.py` импортирует `_v3`. Старые версии пока не удалять: тесты на них есть. Выяснить целевую политику миграции.
- В `.sqlfluff` указан `dialect = teradata`, отступ 4 пробела, leading commas. Проверить версию SQLFluff и повторяемость окружения.

## Порядок исправлений
1. **Baseline:** на целевой машине создать отдельную ветку/копию, проверить `python -m unittest discover -s tests -t . -p 'test_*.py' -v`, классифицировать 4 ERROR, собрать воспроизводимые минимальные SQL и stderr diagnostics. Зафиксировать версию Python и SQLFluff.
2. **Технические ERROR:** исправить пути, CLI-кодировку и ошибки импортов/тестового harness без изменения семантики форматирования.
3. **Границы SELECT/FROM/WHERE:** один AST-scoped механизм для пробелов между клаузами, который не затрагивает литералы и комментарии. Начать с простого `SELECT id, name FROM users WHERE active=1;` и существующих golden-тестов.
4. **Конфликты правок:** определить ownership и атомарность; не использовать silent skip; тестировать перекрытия на вложенных запросах.
5. **JOIN/ON, GROUP/ORDER, HAVING, QUALIFY, CTE, OVER:** последовательно, по матрице контракта и приоритету падений.
6. **Надёжность:** идемпотентность, сохранение токенов и комментариев, DBeaver smoke, Unicode/CRLF, производительность.
