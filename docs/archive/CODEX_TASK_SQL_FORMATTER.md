# Задание Codex: аудит и исправление Teradata SQL Formatter

Ты работаешь с приложенным проектом `SQL_formatter_review.zip`. Прочитай **все** файлы `formatter.py`, `dbeaver_formatter.py`, `formatter_modules/`, `tests/`, `.sqlfluff`, `docs/teradata_formatter_contract_v1.1.md`, `docs/contract_bochenkov.md`, `docs/SQL_formatter_roadmap.md` и приложенный `SQL_FORMATTER_AUDIT.md`.

## Цель
Сделать форматтер Teradata SELECT корректным, безопасным, идемпотентным и пригодным для вызова из DBeaver. **Не заниматься косметической организацией папок.** Текущие имена `formatter.py`, `dbeaver_formatter.py`, `formatter_modules/`, `tests/` сохранить.

## Режим работы
**Фаза A — сначала только аудит, без изменений.**
1. Прочитай контракт v1.1 (при конфликте с v1 уточни расхождения), карту функций и все тесты.
2. Установи зависимости в изолированном окружении при необходимости, зафиксируй версии Python/SQLFluff. Не выполняй потенциально опасные команды.
3. Запусти `python -m unittest discover -s tests -t . -p 'test_*.py' -v` и сохрани полный лог. Отдельно сообщи test count, ERROR, FAIL и причины; не доверяй старым журналам как текущему состоянию.
4. Воспроизведи минимум: `SELECT id, name FROM users WHERE active=1;`, SELECT с комментарием перед полем, FROM/JOIN/ON, GROUP/ORDER, CTE, QUALIFY, OVER, literal с двойным пробелом. Покажи input, actual, expected, diagnostics.
5. Определи реальные корневые причины с файлами/строками и предложи минимальные изменения. Проверь гипотезы аудита, не считай их доказанными без воспроизведения.
6. Предоставь отчёт: подтверждено / гипотеза / вне текущего scope; P0/P1/P2; список файлов для правки; риск регрессии; план PR/коммитов.

**Фаза B — исправления только после согласования плана с пользователем.**
1. Сначала убери технические `ERROR`, не меняя SQL-правила.
2. Исправь границы `SELECT`/`FROM`/`WHERE` на основе AST и точечных пробельных диапазонов. Не разбивай SQL регуляркой по ключевым словам, не трогай содержимое выражений.
3. Устрани конфликты overlapping edits через явный ownership/атомарность, не замалчивай пропуски.
4. По одному блоку: JOIN/ON, GROUP/ORDER, HAVING, QUALIFY, CTE, оконные функции.
5. На каждый дефект: минимальный регрессионный тест, полный прогон, тест идемпотентности и сохранности SQL.

## Жёсткие ограничения
- Не удалять и не ослаблять `validate_sql_unchanged()`, защиту комментариев/литералов, диагностические предупреждения ради прохождения тестов.
- Не менять expected golden-результаты только ради зелёных тестов; при противоречии контракту явно сообщить.
- Не добавлять фиктивный `WHERE 1=1` вне требований контракта; отдельно проверить исключение служебного префикса в валидации.
- Не переписывать проект с нуля, не добавлять `stage10`, `stage11`, новые версии модулей `_v4` без необходимости.
- Не удалять похожие тесты до анализа различий. Не менять DBeaver API и формат stdout без smoke-теста.
- Сохранять UTF-8 и Windows PowerShell совместимость. Если тест запускается из корня, используйте `python -m unittest discover -s tests -t . -p 'test_*.py' -v`.
- Не заявлять, что тесты прошли, если не запускались.

## Формат первого ответа Codex
1. Таблица P0/P1/P2: проблема, доказательство (файл:строка), эффект, предлагаемое решение.
2. Сводка реального прогона тестов и группировка падений по корневым причинам.
3. Трасса одного минимального SQL через `format_sql` с указанием этапа, где теряется граница FROM.
4. Конкретный минимальный план исправлений (не более 3–5 первых задач), с оценкой рисков.
5. Остановись и запроси разрешение на фазу B. **На фазе A код не изменяй.**
