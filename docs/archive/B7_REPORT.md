# B7 — адаптер DBeaver и подготовка к Windows VDI

Baseline: `ee68e7f5006b002dc5e0d2d1fe151c36f696dfcc`, 269 tests, 0 FAIL, 0 ERROR.
Windows/DBeaver пока не проверены фактическим запуском. B8 не нужен и не начат.

## Аудит и согласованное решение

Существующий `dbeaver_formatter.py` принимает один путь, читает UTF-8-sig из
байтов, выдаёт UTF-8 в stdout, диагностирует в stderr. Ошибки аргументов дают 2,
чтения/кодировки/форматирования — 1, успех и консервативный E004 — 0.
`formatter.py` также имеет самостоятельный CLI, с необязательным путём
(по умолчанию input.sql). Оба интерфейса оставлены без изменений.

Исследована [официальная реализация транспорта DBeaver](https://github.com/dbeaver/dbeaver/blob/e97f23bcbd68db782b5300591dc4b61366f30c92/plugins/org.jkiss.dbeaver.model.sql/src/org/jkiss/dbeaver/model/sql/format/external/SQLFormatterExternal.java#L104):
временный файл использует sourceEncoding, затем `${file}` подставляется в команду;
строка 115 объединяет stderr/stdout, строки 127–131 не отвергают результат при
ненулевом exit code. Это подтверждено чтением исходника и моделированием
объединённого потока subprocess на macOS, не запуском самого DBeaver.

Согласован и добавлен отдельный `dbeaver_adapter.py`. Он читает оригинальные
байты до импорта форматтера и напрямую вызывает format_sql с diagnostics=[].
Кандидат дополнительно проверяется неизменённым validate_sql_unchanged, включая
сценарии C001/E002. При E004/E003, неизвестной диагностике, ошибке или неожиданном
Python-выводе возвращается original bytes. Два Python-потока перехватываются,
дескрипторы 1/2 заглушены; завершённый результат пишется в сохранённый stdout.
Windows-ветка устанавливает O_BINARY, исключая преобразование LF через CRT;
проверка этой ветки на Windows остаётся ручной.

Исключения импорта SQLFluff также не попадают в результат. При импорте адаптера
никакие потоки не перенастраиваются. SQL-файл не перезаписывается. Прямой вызов
без дочернего CLI не требует дополнительного запуска Python.

## Доказательства до / после

Вход:

```sql
SELECT id, name FROM users WHERE active=1;
```

Actual = expected, оба прохода:

```sql
SELECT
    id
    , name
FROM users

WHERE active = 1
;
```

Для байтов `EF BB BF` + `SELECT FROM;\r\n` прежний CLI выдавал код 1 и
`Formatting failed: ...` в stderr: при объединении потоков это становилось
содержимым редактора. Теперь actual = expected = все исходные байты, включая
BOM/CRLF, stderr пуст, код 0 (успешная доставка fallback).

Для BOM + `SELECT SUM(a) OVER w\rFROM t;\r\n` прежний объединённый вывод
содержал E004 и SQL. Теперь actual = expected = original bytes, без E004 в
редакторе. Диагностический код остаётся в локальном журнале.

Для `SELECT SUM(a) OVER (PARTITION BY a,\r\n-- detached\r\n\r\nb) AS n FROM t;`
C001/E002 сохранены в журнале; результат проходит строгую проверку, а повторный
вызов побайтно совпадает с первым. Предупреждения не подавлены в форматтере.

## Матрица автоматических проверок

Новый модуль `tests/contract/test_contract_b7.py`, 13 тестовых методов:

| Проверка | Доказательство |
|---|---|
| Успешный SELECT | Точное независимое expected, два прохода |
| Невалидный SQL / E004 / invalid UTF-8 | Побайтный fallback с BOM и CR |
| Unicode, quoted identifiers, literals, block comments | LF/CR/CRLF/mixed, строгий validator, два прохода |
| C001/E002 | Коды в журнале, validator, идемпотентность |
| Исключение и вывод в оба Python-потока | Original bytes, потоки пусты, секрет отсутствует в журнале |
| Ошибочный кандидат форматтера | Строгая валидация отклоняет изменение SQL |
| Неожиданный вывод при успешном возврате | Консервативный побайтный fallback |
| Недоступный журнал | Файл вместо каталога и PermissionError; SQL возвращается |
| Ошибки чтения/аргументов | Пустой объединённый поток, ненулевой код |
| PermissionError чтения/записи | Subprocess + имитация отказа ОС, никаких сообщений |
| Путь проекта и SQL с кириллицей/пробелами, чужая cwd | Копия проекта, hostile .sqlfluff, точный expected |
| Импорт модулей | Нет вывода и изменения объектов/кодировок потоков |
| Отсутствие зависимости | Python -S: ошибка импорта, original bytes без traceback |
| Старый CLI | Прежние stdout/stderr/exit codes |
| Журнал | Ротация, фиксированный набор безопасных полей |

Несколько строк таблицы проверяются одним методом. Слияние stderr=STDOUT и
игнорирование кода при получении результата моделируют опасный транспорт
DBeaver. Существующие B6 тесты дополнительно проверяют независимость от
пользовательских конфигураций; полный набор сохраняет проверки атомарности,
protected spans, токенов, casing и AST-областей B2–B6.

## Журнал и ограничения

По умолчанию LOCALAPPDATA/SQLFormatter/logs на Windows, иначе системный temp.
SQL_FORMATTER_LOG_DIR позволяет выбрать разрешённый каталог. JSONL содержит
UTC timestamp, фиксированный диагностический код, класс ошибки и безопасное
описание. Нет SQL, traceback, исходных путей или сообщений исключений. Ротация
после ~256 KiB, один backup; при конкурентной ротации запись может потеряться,
но SQL от журнала не зависит.

Если байты вообще не прочитаны, исходник восстановить нельзя: READ возвращает
1 и пустой вывод. При отказе трубы вывод не гарантирован; после частичной записи
fallback не дописывается. Ошибки запуска Python до выполнения адаптера,
принудительное завершение/timeout и поведение редактора при пустом выводе
не могут быть устранены внутри скрипта. На реальном DBeaver обязательна проверка
этих сценариев на копии SQL. Безусловная безопасность при любом системном сбое
не заявляется.
