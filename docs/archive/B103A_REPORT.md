# B10.3a — диагностика атомарного отказа процедур

Ветка: `feature/b10-stored-procedures`. Исходная версия B10.2: `7cfb7b3198c928c5e6ce6c87bc0aadb286683963` (345 тестов). Исследован локальный приватный образец; его содержимое, имена объектов, литералы и имя файла в этот отчёт и репозиторий не включены.

## Причина и этап отказа

Причина — накопление процедурного отступа на продолжениях многострочного DML. Это не ошибка грамматики. В `formatter_modules/formatter_procedure.py:35` функция `indented_fragment()` добавляет отступ блока к продолжениям строк вне защищённых участков. Вложенный `dml()` (строка 158) передаёт исходный текст DML обычному форматтеру и затем снова добавляет процедурный отступ. Обычный форматтер сохраняет некоторые произвольные LF-переносы внутри выражений, включая IN/NOT IN. На втором проходе сохранённый отступ уже содержит отступ процедуры, который добавляется повторно.

На приватном образце оба профиля показывают одинаковую последовательность:

| Этап | Результат |
|---|---|
| Чтение исходных байтов, выбор personal/corporate, декодирование | Успешно |
| Процедурная грамматика | Без violations/unparsable |
| Layout, вложенный DML, атомарный planner | Успешно |
| CP01–CP05 | Успешно |
| Строгая валидация, включая protected spans | Успешно на обоих внутренних проходах |
| Сравнение первого и второго кандидатов | NON_IDEMPOTENT |
| Атомарный возврат | SQLFMT-E003, исходный SQL целиком |

Первая разница — смещение 1889 в первом кандидате (нулевая нумерация), строка 71. Это координаты кандидата, не исходного файла. Исследование различий выявило 22 вставки по четыре пробела; прочие символы не меняются. Затронуты продолжения внутри `bracketed` и `expression`. Нормализованный регистр также откатывается вместе со всем результатом — поэтому редактор показывает полностью неизменённый SQL.

## Минимальное обезличенное воспроизведение

Вход:

```sql
CREATE PROCEDURE p() BEGIN INSERT INTO t SELECT a FROM u WHERE a IN (1,
2); END;
```

Первый внутренний кандидат:

```sql
CREATE PROCEDURE p()
BEGIN
    INSERT INTO t
    SELECT
        a
    FROM u

    WHERE a IN (1,
    2)
    ;
END;
```

Во втором внутреннем кандидате перед `2)` уже восемь пробелов вместо четырёх. Оба кандидата проходят строгую валидацию SQL, но не совпадают побайтно. Публичный вызов возвращает исходный SQL и E003. В тесте приватный однопроходный вызов используется исключительно для исследования; публичная проверка повторного прохода и атомарный откат не отключены.

Ожидание диагностического регрессионного теста — воспроизвести этот отказ и подтвердить сохранность исходника. Это не исправление дефекта. Для B10.3b требуется стабильный отступ при повторном вызове, без изменения относительной раскладки выражения и protected spans.

## Синтетическая матрица

| Конструкция | AST | Публичный результат |
|---|---|---|
| Block comment между SQL SECURITY INVOKER и BEGIN | PASS | Форматируется, идемпотентно |
| CAST(... AS TIMESTAMP(6)) | PASS | Форматируется, идемпотентно |
| INTERVAL '1' SECOND | PASS | Форматируется, идемпотентно |
| Конкатенация `\|\|`, TO_CHAR/COALESCE, CALL | PASS | Форматируется, идемпотентно |
| Скобки, OR и BETWEEN в DELETE | PASS | Форматируется, идемпотентно |
| Два последовательных INSERT SELECT | PASS | Форматируется, идемпотентно |
| Однострочные IN и NOT IN, 50 элементов | PASS | Форматируется, идемпотентно |
| Многострочные IN и NOT IN, 2–3 элемента | PASS | Воспроизводится E003 на повторном проходе |
| Неподдержанный IF/THEN | UNPARSABLE | Отказ на parse; CP не запускается |

Следовательно, длина списка сама по себе не является причиной. Минимальный триггер — сохранённое продолжение строки при вложении DML в процедуру. Для воспроизведения проверены LF, CR, CRLF, смешанные окончания и BOM: исходник возвращается точно. Оба профиля и адаптер с объединёнными stdout/stderr проверены subprocess-тестом; в выходе только исходные байты SQL.

## Безопасная диагностика

Добавлен `formatter_modules/formatter_trace.py`: включение только через `SQL_FORMATTER_TRACE=1`. Файл `diagnostic.jsonl` создаётся в `SQL_FORMATTER_LOG_DIR`, по умолчанию `%LOCALAPPDATA%/SQLFormatter/logs` (при отсутствии переменной — временный каталог). Поля ограничены: время, PID, этап, код, разрешённый тип сегмента, позиция, система координат, длительность, разрешённый класс исключения. Не записываются SQL, raw-сегменты, текст исключений, имена файлов или выбранные объектные имена. Ошибки записи журнала не меняют результат SQL.

Добавлены измерения в процедуру и адаптер без изменения решений о форматировании. Существующий журнал адаптера сохраняется. При выключенной трассировке новый журнал не создаётся. Проверены отсутствие утечки контрольного секретного текста, отсутствие stdout/stderr и недоступный каталог журнала.

`diagnose_formatter.py` — отдельный локальный инструмент без GUI и без вывода SQL. Он читает байты, выбирает существующий маршрут профиля и записывает метаданные. Код выхода 0 означает завершение диагностики, включая безопасный отказ; 1 — ошибку запуска/чтения, 2 — неверные аргументы. Причину форматирования смотреть в журнале. Не подставлять этот инструмент вместо адаптера в DBeaver: он намеренно не выводит SQL.

Из корня установленного проекта, Windows cmd.exe:

```bat
".venv\Scripts\python.exe" -B diagnose_formatter.py "C:\Private\input.sql" personal "%LOCALAPPDATA%\SQLFormatter\logs\b103-personal"
".venv\Scripts\python.exe" -B diagnose_formatter.py "C:\Private\input.sql" corporate "%LOCALAPPDATA%\SQLFormatter\logs\b103-corporate"
```

Для трассировки реального GUI установить `SQL_FORMATTER_TRACE=1` и `SQL_FORMATTER_LOG_DIR` в окружении **до запуска DBeaver**, сохранив существующую команду адаптера. Уже запущенный DBeaver новое окружение не наследует. После диагностики удалить переменную (`set "SQL_FORMATTER_TRACE="`) и перезапустить приложение. GUI-фаза включает время выбора пользователем; это не время работы движка.

## Замечания ручной приёмки, отложенные

Зафиксированы для следующего согласованного этапа: `LEFT JOIN (` на одной строке; вложенный SELECT с новой строки и дополнительным уровнем; пробел после закрывающей скобки перед алиасом; ON на уровне JOIN; первый верхнеуровневый оператор с нулевого отступа. Эти правила в B10.3a не изменялись. Задержка после выбора профиля измерена, но не оптимизирована.

## Предложение B10.3b

Исправлять композицию отступов в `dml()`/`indented_fragment()`, а не грамматику или строгую валидацию. Перед повторным вложением DML нужно выделить его доказуемый внешний отступ в исходном AST-контексте и приводить только внешние whitespace-промежутки к локальной системе отступов. Затем добавлять целевой уровень блока ровно один раз, сохраняя относительную раскладку продолжений. Нельзя применять blanket lstrip/dedent, менять protected spans или отключать проверку повторного прохода. При неоднозначном исходном отступе — консервативный отказ.

Проверить IN/NOT IN, многострочные выражения и функции, вложенные циклы, комментарии, защищённые многострочные значения, CR/CRLF/BOM, оба профиля. Изменение должно устранить именно накопление внешнего отступа, не расширяя правила произвольных LF-переносов обычного SQL. До согласования B10.3b этот алгоритм не реализован.
