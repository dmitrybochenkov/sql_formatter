# Контракт Teradata SQL Formatter

Актуальное поведение B10.4; архитектурная и тестовая консолидация B10.3c–d сохранена. Исторические редакции находятся в `archive/`. Здесь **Implemented** означает подтверждённое тестами поведение поддержанного подмножества; **Known issue** — известное ограничение/замечание; **Planned** — будущую работу, не гарантию текущей версии.

## Общие гарантии

| Статус | Правило |
|---|---|
| Implemented | SQLFluff **4.4.0**, диалект Teradata; процедурная грамматика проекта подключается через общий selector runtime/CP. Установленная библиотека не модифицируется. |
| Implemented | Изменяются оформление и доказанный регистр, но не порядок выражений, операторов, аргументов или семантическая структура SQL. Узкие исключения для `WHERE/HAVING 1=1` и удаления необязательного табличного `AS` описаны ниже. |
| Implemented | Повторное форматирование поддержанных сценариев побайтно идентично. Процедура обязательно проходит внутренний повтор до выдачи результата. Обычный SQL проверяется регрессиями, без нового глобального повторного прохода runtime. |
| Implemented | Строгая проверка количества, типа, порядка и AST-принадлежности токенов; точная последовательность protected spans по типу и содержимому. Разрешённые CP-изменения, синтетические префиксы и удаление необязательного табличного AS доказываются отдельно по исходному AST. |
| Implemented | Edit planner проверяет границы, пересечения и protected spans. Связанные edits применяются атомарно. Независимые безопасные группы обычного SQL могут применяться при отказе другой группы. |
| Implemented | Процедура — единая транзакция: ошибка, конфликт, неоднозначность или нестабильный повтор возвращают весь исходник. Адаптер DBeaver дополнительно валидирует результат и возвращает исходные байты при ошибке. |
| Known issue | Полная канонизация произвольных исходных LF-переносов не достигнута. Нельзя считать все синтаксически допустимые Teradata-запросы поддержанными. |

## Защищённые участки, кодировки и окончания строк

**Implemented:** строковые литералы, quoted identifiers, `--` и `/* ... */` комментарии сохраняют точное содержимое, включая пробелы, кавычки, CR, LF и CRLF. Пробельный отступ *перед* комментарием не является его содержимым; может меняться только при доказанной привязке. Разделитель строки после `--` находится вне содержимого комментария.

**Implemented:** вход может содержать LF, CRLF, CR и смешанные окончания. Для parser-view строится проверяемая карта смещений в оригинал. Edits применяются к оригиналу; вне protected spans канонический разделитель — LF. Внутри protected spans окончания не меняются, поэтому итог может содержать смешанные окончания. При полном отказе возвращается исходник с исходными окончаниями.

**Implemented:** файловый транспорт использует UTF-8. Чтение производится как bytes, без universal-newline преобразования. Для процедур исходный UTF-8 BOM сохраняется также при успехе; обычный SQL при успешном файловом вызове сохраняет установленное поведение B8 — результат без BOM. При отказе адаптер сохраняет исходные bytes, включая BOM и некорректную кодировку. Это различие транспорта и строкового `format_sql()` не скрывается.

## SELECT, FROM, списки и алиасы

**Implemented:** отступ уровня — четыре пробела. SELECT и распознанные модификаторы DISTINCT/ALL/TOP остаются заголовком; поля — на строках с +4, второе и последующие с ведущей `, `. Звёздочки являются обычными элементами. Между последним полем и FROM нет пустой строки. Однотабличный FROM остаётся `FROM table_name alias`; следующие таблицы comma-FROM — на строках +4 с ведущей запятой.

```sql
SELECT DISTINCT
    t.id
    , t.name
FROM users t
    , roles r
;
```

**Implemented:** выражения/аргументы не разделяются по текстовым запятым; используются AST-границы. Запятые литералов и функций не становятся разделителями внешнего списка. Порядок модификаторов и элементов не меняется. Имена алиасов не добавляются/удаляются; разрешённый регистр определяется CP02. Необязательный AS табличного алиаса удаляется только в доказанном AST-контексте FROM/JOIN для обычной таблицы или derived table. Между таблицей/закрывающей скобкой и алиасом остаётся один пробел. AS колонок, выражений, CAST и определения CTE сохраняется. Комментарии в промежутке таблица–AS–алиас, функции вместо таблиц, списки колонок алиаса и нестандартные формы исключаются из этого преобразования. Валидатор разрешает только удаление конкретного исходного AS; вставка AS, изменение имени или перенос токенов между табличными областями не разрешены. Пробелы простых сравнений оформляются без разрыва составных операторов.

**Implemented B10.4:** для однозначного derived-table alias в FROM/JOIN используется `) alias`, включая исходный `)alias`. Между скобкой и алиасом не должно быть комментария или нестандартной синтаксической конструкции; такие фрагменты сохраняются консервативно.

## JOIN и ON

**Implemented для обычного JOIN без подзапроса:** пустая строка перед JOIN, ON на том же уровне, без пустой строки между JOIN и ON. Непосредственные AND в ON получают +4; сравнения разделяются пробелами. Служебный `1=1` в ON не добавляется. Комментарий непосредственно перед JOIN сохраняет принадлежность.

```sql
FROM users u

LEFT JOIN events e
ON e.user_id = u.id
    AND e.status = 'OK'
```

**Implemented B10.4 для прямого JOIN с derived table:** `LEFT JOIN (` на одной строке; SELECT с новой строки на +4; закрывающая скобка на уровне JOIN, затем пробел и алиас. Поддержаны INNER/RIGHT/FULL OUTER и допустимый CROSS JOIN, последовательные и вложенные derived JOIN, CTE, INSERT SELECT и процедурный DML. ON остаётся на уровне JOIN по прежнему правилу. Новый обработчик не расширяет поддержку USING и скобочных деревьев JOIN без derived SELECT. Неоднозначные комментарии сохраняют существующий консервативный отказ.

## WHERE и HAVING

**Implemented:** самостоятельные блоки с пустой строкой перед ними. Один предикат — без синтетического `1=1`. При минимум двух непосредственных условиях, соединённых AND, и отсутствии верхнеуровневого OR разрешён ровно один `1=1`, затем ведущие AND с +4. Уже существующий префикс повторно не добавляется.

```sql
WHERE 1=1
    AND a = 1
    AND b > 0

HAVING 1=1
    AND COUNT(*) > 1
    AND SUM(amount) > 100
```

**Implemented:** AND внутри BETWEEN, рамок окон, вложенных булевых скобок и подзапросов не считается непосредственным AND внешней области. Валидатор подтверждает вставку по исходному AST конкретного WHERE/HAVING. Внешний и внутренний WHERE, разные CTE/ветви и процедурные операторы не обмениваются префиксами. Удаление/изменение исходного выражения, второй префикс или вставка в ON/QUALIFY запрещены.

**Implemented:** смешанный верхнеуровневый AND/OR не перестраивается, приоритет скобок сохраняется, префикс не вставляется. Не обещается отдельная диагностика для каждого допустимого смешанного выражения: историческое желаемое предупреждение не равно обязательному текущему runtime-сообщению.

## GROUP BY, ORDER BY и пустые строки

**Implemented:** перед GROUP BY/ORDER BY — одна пустая строка. Один элемент может находиться в строке заголовка; несколько элементов — вертикально, +4, ведущие запятые. ASC/DESC и NULLS FIRST/LAST остаются при своих выражениях; CP может нормализовать их регистр. Оконный ORDER BY отделён AST-контекстом от внешнего.

**Implemented:** в поддержанных блоках одна пустая строка между самостоятельными клаузами; исключения — SELECT/FROM и JOIN/ON без пустой строки, а также части OVER без пустых строк. В списках лишние пустые строки нормализуются только при безопасной привязке. Комментарии не считаются пустыми строками и не удаляются ради нормы. Терминальный `;` обычного SQL — отдельная строка, финальный LF вне protected spans.

**Known issue:** произвольные внутренние переносы выражений могут сохраняться. Не следует выводить из правил блоков разрешение переписать любой whitespace SQL глобальной заменой.

## Вложенные запросы, CTE и операции над множествами

**Implemented в покрытых AST-контекстах:** вложенный SELECT в FROM и WHERE IN/EXISTS начинается с новой строки; уровень рассчитывается по AST. SELECT/FROM сохраняют общую связку без пустой строки. Закрывающая скобка соотносится с содержащей конструкцией. Внешние широкие правки не захватывают внутренний SELECT.

**Implemented:** `WITH name AS (` — заголовок CTE, тело +4, `)` на уровне заголовка. Следующие CTE отделяются пустой строкой и ведущей запятой. Между последним CTE и основным запросом — пустая строка. Поддержаны несколько CTE и согласованные сочетания с set operations; комментарии/неоднозначные границы остаются под защитой.

**Implemented:** UNION/UNION ALL/INTERSECT/поддержанный EXCEPT на собственной строке с пустой строкой до и после. Каждая SELECT-ветвь оформляется в своей области. Порядок операторов и скобок не меняется, общий ORDER BY не переносится внутрь ветви.

**Known issue:** поддержка прямых derived-table JOIN не означает поддержку всех возможных выражений SELECT и JOIN-деревьев. Неоднозначные AST-конструкции сохраняются консервативно.

## OVER и QUALIFY

**Implemented:** поддержанные оконные выражения раскрывают OVER на несколько строк. PARTITION BY и оконный ORDER BY используют компактный одиночный либо вертикальный множественный список. Между ними и ROWS/RANGE нет пустых строк. Рамки, границы, направления сортировки и порядок токенов сохраняются. Скобка окна выравнивается относительно содержащего выражения. Несколько окон и внешний ORDER BY независимы.

**Implemented:** QUALIFY — самостоятельный блок, первое условие после QUALIFY на той же строке. Непосредственные AND получают +4; OR и смешанная логика сохраняют группировку. `1=1` не добавляется. Окна внутри QUALIFY используют оконный контекст. Поддержаны согласованные сочетания с CTE и ветвями множеств.

**Implemented отказ:** неподдержанные именованные окна сохраняют SQLFMT-E004 и исходник. **Planned:** расширение охвата окон требует отдельного контракта, не входит в B10.3c.

## Комментарии и многострочные выражения

**Implemented:** комментарий справа остаётся у предыдущего выражения; при переносе завершающей запятой ведущая запятая помещается после комментария, а не под `--`. Самостоятельный комментарий перед элементом, однозначная цепочка, block comment сохраняют содержимое и доказанную принадлежность. GROUP/ORDER используют точечные edits, перемещение запятой — атомарную группу.

**Implemented:** пустая строка, отделяющая комментарий от следующего элемента, означает неоднозначность: существующий C001 и отказ от затронутого преобразования. Нельзя угадывать принадлежность смешанной цепочки. В обычном SQL независимые безопасные участки могут форматироваться; в процедуре неоднозначность вызывает полный откат.

**Implemented:** B10.3b сохраняет относительные отступы многострочных IN/NOT IN, выражений, скобок и функций при добавлении внешнего процедурного уровня. **Known issue:** это не новая каноническая раскладка произвольных многострочных выражений обычного SQL.

## Регистр CP01–CP05

**Implemented:** только штатные SQLFluff LintFix из CP01–CP05, без запуска полного `sqlfluff fix`:

| Правило | Политика |
|---|---|
| CP01 | Keyword-токены UPPERCASE |
| CP02 | Неquoted identifiers/алиасы lowercase |
| CP03 | Имена функций UPPERCASE |
| CP04 | Булевы/NULL literals UPPERCASE |
| CP05 | Типы данных UPPERCASE |

Строки в кавычках, quoted identifiers и комментарии не меняются. Принимается только однозначный leaf-token replace доказанного upper/lower-варианта той же длины и AST-принадлежности. Ни вставки/удаления, ни общее casefold-сравнение не разрешены. Все case-edits — одна атомарная группа. Несопоставимый AST, Unicode-изменение длины или конфликт вызывают отказ. Оба профиля используют эти же правила.

## Процедуры

**Implemented:** одна процедура `CREATE/REPLACE PROCEDURE name(...) [SQL SECURITY INVOKER] BEGIN ... END;`; IN/OUT/INOUT-параметры; DECLARE с типом и поддержанным literal DEFAULT; SET; CALL с выражениями; WHILE ... DO ... END WHILE; вложенные BEGIN/END; DELETE и INSERT INTO ... SELECT внутри блоков; последовательные операторы и циклы. Корпоративная приватная процедура локально прошла проверку B10.3b, но это не подтверждение всего синтаксиса Teradata.

**Implemented layout:** заголовок/параметры, SQL SECURITY INVOKER и BEGIN разделяются; списки параметров/CALL используют ведущие запятые; тело +4 на каждый блок/цикл. Закрывающие END/END WHILE выровнены с началом блока. Смежные DECLARE и смежные SET не разделяются пустой строкой; между разными единицами — пустая строка. DML использует существующие SELECT/JOIN/WHERE-правила на уровне блока. DML `;` следует существующему SQL-оформлению; procedural `;` примыкает к своему оператору/закрытию.

**Implemented B10.3b:** из продолжений DML убирается доказуемый внешний отступ его исходной строки, затем целевой уровень применяется один раз. Внутренние строки protected spans непрозрачны. Недостаточный/неоднозначный внешний отступ не угадывается: E003 и исходная процедура. Сохраняются BOM и политика окончаний строк.

**Implemented безопасность:** явные AST-сегменты, соответствие BEGIN/END и WHILE/END WHILE, границы операторов и исполнения, строгая валидация и внутренний повтор. Нет regex-разбиения процедуры или непрозрачных raw-блоков вместо грамматики.

**Known issue / ограничение:** SQLFluff должен быть ровно 4.4.0; используется изолированный приватный dialect-object hook. IF/ELSE, handlers, cursors, labels и другие неподдержанные процедурные конструкции, а также scripts из нескольких процедур не обещаны; ошибка разбора приводит к полному отказу. Комментарии внутри некоторых параметрических/CALL-списков пока вызывают C001. Низкоуровневый `parse_procedure()` — диагностический LF-only helper; runtime использует SourceMap и поддерживает CR/CRLF.

**Implemented B10.4:** верхнеуровневые SELECT/WITH/INSERT/UPDATE/DELETE начинаются с нулевой колонки. Удаляется только доказанный пробельный префикс непосредственного statement корневого AST; после оператора или комментария на той же строке добавляется граница строки. Существующие пустые строки между операторами, содержимое комментариев и protected spans сохраняются. Внешний уровень процедурных блоков по-прежнему добавляет процедурный renderer; глобальные lstrip/dedent не применяются.

## Интеграция, ошибки и диагностика

**Implemented:** `format_sql(source, diagnostics=None)` и `validate_sql_unchanged()` остаются библиотечными интерфейсами. `formatter.py [path]` — headless CLI (по умолчанию input.sql), SQL в stdout, диагностика/ошибки в stderr. Ошибки обычного SQL могут поднимать исключение; библиотека не обязана во всех случаях возвращать исходник сама.

**Implemented:** единственная официальная точка входа DBeaver — `dbeaver_adapter.py path`. GUI `formatter_modules/profile_selector.py` выбирает personal/corporate по 1/2 без Enter, Esc/крестик отменяют; кнопки доступны мышью. Tk загружается только при необходимом уведомлении/выборе. Ошибка GUI не запускает автоматическое форматирование. Конфигурация обоих профилей общая; PROFILE_FORMATTERS маршрутизирует безопасный bytes-транспорт, не дублирует движок.

**Implemented:** адаптер читает bytes, перехватывает вывод, валидирует результат и выдаёт только SQL. C001/E001/E002 допускают лишь проверенный результат; E003/E004, неизвестная диагностика, исключение и неожиданный вывод возвращают исходные bytes. Отмена тоже возвращает исходник. Код 0 означает доставленный SQL, включая fallback. Непрочитанный файл, оборванный выход, timeout/убийство процесса и ошибка запуска Python находятся за пределами гарантии доставки исходника. Подробности — [инструкция](DBEAVER_WINDOWS_SETUP.md).

**Implemented:** `tools/diagnose_formatter.py path personal|corporate log_directory` — отдельная headless-диагностика, не выводит SQL и не заменяет адаптер. `SQL_FORMATTER_TRACE=1` явно включает безопасные метаданные этапов, типов сегментов, смещений и времени. Исходный SQL, литералы, имена объектов и текст исключений не журналируются. Ошибка журнала не меняет SQL. Конфигурация SQLFluff строится программно из immutable профиля, без .sqlfluff/cwd/home/noqa-конфигурации из SQL.

**Known issue:** ручная приёмка Windows/VDI, фокус Tk и поведение конкретной версии DBeaver при timeout ещё не завершены. **Planned:** DDL и оптимизация производительности — отдельные этапы [roadmap](ROADMAP.md).

## B10.5f: пользовательский профиль

[Пять групп параметров, правила сравнения и уведомлений](USER_CONFIGURATION.md) — часть контракта. Стандартные настройки побайтно сохраняют B10.5a–e. Для `group_by.layout="multiline"` один элемент всегда `GROUP BY a`; два и более построчно. Corporate встроен, Personal необязателен и читается только из локального пользовательского каталога (Windows: `%LOCALAPPDATA%\SQLFormatter\personal.toml`; платформенные пути — в инструкции). Шаблон `config_templates/personal.example.toml` не активен. Отсутствие/удаление Personal означает Corporate без предупреждения, без автосоздания и поиска рядом с проектом. Выбор появляется только при валидных отличиях. CP-доказательства допускают только конкретный результат выбранного upper/lower правила; preserve отключает соответствующее правило, без общего разрешения менять токены. Настройки не отключают protected spans, AST ownership, planner, validator или procedural repeat.


## Именованные параметры, выбор профиля и Python 3.10

В выражениях Teradata поддерживаются bind-токены `:[A-Za-z_][A-Za-z0-9_]*` через локальную грамматику SQLFluff 4.4.0, общую для runtime и CP. Это не подстановка значений и не placeholder templater. Имя и регистр параметра неизменны; количество, порядок и AST-принадлежность проверяются прежним строгим валидатором. Строки/комментарии/quoted identifiers не становятся параметрами. Пробел между двоеточием и именем, цифровое начало, подстановка имени таблицы и неподдержанные colon-конструкции не разрешаются; rollback сохранён. `::` остаётся отдельной casting-конструкцией SQLFluff.

Corporate SQL-правила не изменены. `[profile_selector] timeout_seconds` (целое 1–60, default 3) — UI-настройка вне сравнения пяти SQL-групп и fingerprint SQL-политики. Нет Personal/нет SQL-отличий → Corporate без окна. При отличиях → одно окно, `1` Personal, `2` Corporate, timeout автоматически Personal; Esc/крестик отменяет. Валидные изменения больше не вызывают отдельный алерт; state нужен только для однократных предупреждений об ошибках Personal. Snapshot текущего вызова неизменен. При ошибке GUI исходный SQL сохраняется.

Python 3.10 использует условную зависимость tomli; 3.11+ — tomllib. CLI поддерживает `-h`/`--help`; прежний файловый режим и DBeaver transport сохранены. Opt-in trace дополнен колонкой проблемного AST-сегмента. Содержимое SQL и пользовательские пути не журналируются. Ручные шаги и ограничения — в `tests/manual/README.md`.

## B10.6 — явные скобочные списки и Unicode

Встроенный Corporate сохраняет прежнюю раскладку. Только явный Personal
`layout.parenthesized_lists.mode` включает `single_line`, `multiline` или
`adaptive`; лимит 20–1000 (default 100) действует только в adaptive. Обрабатываются
AST-списки IN/NOT IN и строки VALUES, но не подзапросы и не произвольные скобки.
Меняются лишь межэлементные gaps и запятые одной атомарной группы; содержимое
выражений и protected spans не переписывается. Комментарии заставляют сохранить
безопасную построчную форму. Неоднозначность — C001 и отказ от всей группы.
Adaptive считает префикс/суффикс строки и внешний процедурный отступ, переносит
только целые элементы. Связанные границы нескольких списков доводятся до
устойчивой раскладки с ограничением числа проходов; цикл или отсутствие сходимости
означают отказ, а не выдачу промежуточного SQL. Неразрывный элемент или текст вне
управляемого списка могут превышать soft limit. Это не глобальное ограничение
длины каждой строки SQL. Аргументы функций внутри элемента не переформатируются.

Private Teradata grammar распознаёт Unicode-идентификаторы без ASCII-маскирования.
Исходная последовательность кодовых точек и регистр Unicode-идентификатора
сохраняются: CP02 для него не применяется. Ни NFC/NFD, ни casefold текста не
производятся. ASCII-политика CP01–CP05 остаётся прежней; остальные строгие проверки
типов, AST-принадлежности, токенов и protected spans сохраняются.
Серверные ограничения session charset/NameValidationRule и каталог объектов
форматтер не проверяет. Публичный transport DBeaver не меняется.
