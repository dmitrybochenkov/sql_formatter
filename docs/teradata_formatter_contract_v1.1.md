# Контракт форматтера Teradata SQL

**Версия:** 1.1 — согласованная редакция, 14.10.2026  
**Статус:** правила согласованы; реализация и тесты ещё подлежат проверке.  
**Назначение:** единый источник требований для `formatter.py` и эталонных тестов.

## 1. Базовые принципы

1. Форматтер изменяет **оформление**, а не смысл SQL: не переставляет выражения, поля, таблицы, условия, алиасы и комментарии; не меняет литералы.
2. Повторное форматирование не должно менять результат: `format(format(sql)) == format(sql)`.
3. Один уровень вложенности = **4 пробела**. Табуляции в создаваемых отступах не используем.
4. В списках применяется **ведущая запятая**. В условиях, которые форматируются вертикально, применяется **ведущий `AND`**.
5. Пустые строки внутри списков элементов удаляются; между самостоятельными блоками — **ровно одна пустая строка**, с исключениями, перечисленными ниже.
6. Строки, содержащие только пробелы/табуляции, считаются пустыми. Комментарии пустыми строками **не считаются**.
7. Если участок нельзя безопасно преобразовать, его оставляют без изменений и выводят предупреждение (см. §10); независимые участки форматируются.
8. **Полная нормализация оформления:** случайные исходные отступы, табуляции, пробелы, переносы и пустые строки внутри поддерживаемых конструкций не сохраняются. Один и тот же SQL с разным исходным оформлением должен давать одинаковый канонический результат. Исключения: строковые литералы, текст комментариев и участки, которые нельзя безопасно преобразовать.

## 2. SELECT и FROM — единая связка

- `SELECT` и его модификаторы (`DISTINCT`, `ALL`, распознанный `TOP n`) образуют заголовок на одной строке.
- **Каждое поле SELECT — на отдельной строке** с отступом +4 пробела; у второго и последующих полей ведущая запятая.
- `*` и `alias.*` — обычные поля списка.
- **Между последним полем SELECT и соответствующим FROM нет пустой строки** — в том числе внутри CTE и вложенных запросов.
- Однотабличный FROM остаётся в одной строке: `FROM schema.table t`.
- При нескольких таблицах, перечисленных через запятую, следующая таблица — на новой строке с ведущей запятой.
- Комментарий справа от поля остаётся у этого поля; запятая следующего поля переносится на следующую строку **после комментария**, а не попадает под действие `--`.

```sql
-- Вход
SELECT DISTINCT t.user_id, t.name -- Имя
FROM prd.users t, prd.roles r;

-- Ожидаемый формат
SELECT DISTINCT
    t.user_id
    , t.name -- Имя
FROM prd.users t
    , prd.roles r
;
```

## 3. Границы блоков и пустые строки

- Между самостоятельными блоками запроса (`FROM` → `JOIN`, `FROM` → `WHERE`, `WHERE` → `GROUP BY`, `GROUP BY` → `HAVING`, `HAVING` → `QUALIFY`, `QUALIFY` → `ORDER BY` и т. п.) — одна пустая строка.
- Перед каждым следующим JOIN — одна пустая строка; **между строкой JOIN и его ON пустой строки нет**.
- **Исключение:** между `SELECT` и `FROM` пустых строк нет.
- Внутри списков SELECT, FROM, GROUP BY, ORDER BY и вертикальных условий пустых строк нет; **между соседними CTE** — одна пустая строка.
- Лишние пустые строки схлопываются, пробелы в пустых строках удаляются.
- Комментарии не считаются пустыми строками и не должны перемещаться ради механического выполнения нормы пустых строк.

## 4. JOIN / ON

- `JOIN` и `ON` находятся **на одном уровне отступа**.
- Следующие условия `AND` в `ON` — на новых строках с отступом +4 пробела относительно `ON`.
- В `ON` **не добавляется `1=1`**.
- Перед следующим JOIN — одна пустая строка.

```sql
FROM users t

INNER JOIN sales s
ON s.user_id = t.id
    AND s.status = 'OK'

LEFT JOIN regions r
ON r.id = t.region_id
```

## 5. WHERE и HAVING

- Если есть **два и более условия, соединённые AND**, они выводятся вертикально, с ведущими `AND`, а в начало блока добавляется `1=1`.
- При одном условии `1=1` не добавляется.
- Повторное форматирование не должно добавлять второе `1=1`.
- `AND` внутри `BETWEEN ... AND ...`, оконного `ROWS BETWEEN ... AND ...` и других неделимых конструкций **не считается разделителем условий**.
- Преобразование не должно менять приоритет `AND`/`OR`.

```sql
WHERE 1=1
    AND t.active = 1
    AND t.amount > 0

HAVING 1=1
    AND COUNT(*) > 1
    AND SUM(t.amount) > 100
```

**Смешанные `AND`/`OR` верхнего уровня:** логическое выражение не перестраивать, `1=1` не добавлять; выдать предупреждение. `OR` внутри скобок не препятствует безопасному разделению внешних `AND`.

## 6. GROUP BY и ORDER BY

- При двух и более элементах — вертикальный список с ведущей запятой.
- Для одного элемента допустима компактная запись в строке заголовка.
- Между элементами списка пустых строк нет.

```sql
GROUP BY
    t.user_id
    , t.status

ORDER BY
    t.created_at DESC
    , t.user_id
```

## 7. CTE и вложенные запросы

- `WITH cte_name AS (` — заголовок CTE; тело запроса — с отступом +4 пробела.
- Закрывающая `)` выровнена по уровню заголовка CTE.
- **Между соседними CTE — одна пустая строка**; у второго и следующих CTE — ведущая запятая.
- **Между последним CTE и основным SELECT — одна пустая строка**.
- Во всех вложенных запросах действуют те же правила SELECT/FROM и границ блоков.

```sql
WITH sales AS (
    SELECT
        user_id
        , SUM(amount) AS total
    FROM payments

    GROUP BY user_id
)

, users AS (
    SELECT
        user_id
        , name
    FROM customers
)

SELECT
    u.name
    , s.total
FROM users u

INNER JOIN sales s
ON u.user_id = s.user_id
;
```

- Подзапросы внутри `FROM`, `JOIN`, `WHERE` и выражений `SELECT` должны сохранять исходную вложенность и смысл.

## 8. Оконные функции OVER (...)

- `OVER (` **всегда раскрывается** на несколько строк, включая простые окна.
- `PARTITION BY` и `ORDER BY` внутри окна при нескольких элементах оформляются вертикально с ведущими запятыми.
- Между `PARTITION BY`, `ORDER BY` и `ROWS`/`RANGE` **нет пустых строк**.
- Оконный `AND` в `ROWS BETWEEN ... AND ...` не обрабатывается как логическое условие; `1=1` внутрь окна не вставляется.
- Закрывающая скобка окна выравнивается по отступу выражения, содержащего `OVER`.

```sql
SELECT
    ROW_NUMBER() OVER (
        PARTITION BY
            user_id
            , event_type
        ORDER BY
            created_at DESC
            , event_id DESC
    ) AS rn
    , SUM(amount) OVER (
        PARTITION BY user_id
        ORDER BY created_at
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS rolling_amount
FROM events
```

## 9. QUALIFY

- `QUALIFY` — отдельный блок; перед ним одна пустая строка.
- Первое условие начинается **на той же строке, что и `QUALIFY`**.
- Следующие условия `AND` располагаются вертикально с отступом +4 пробела.
- В `QUALIFY` **не добавляется `1=1`**.
- Вложенные окна раскрываются по §8; скобки и логика `AND`/`OR` сохраняются.

```sql
SELECT
    user_id
    , amount
FROM payments

QUALIFY ROW_NUMBER() OVER (
    PARTITION BY user_id
    ORDER BY payment_date DESC
) = 1
    AND SUM(amount) OVER (
        PARTITION BY user_id
    ) > 10000
;
```

## 10. Комментарии и предупреждения

### Допустимое размещение

1. Комментарий **над следующим SQL-блоком** — непосредственно перед его ключевым словом.
2. Комментарий **над следующим элементом внутри блока** — непосредственно перед элементом (например, перед `, field` или `AND condition`). Запрета таких комментариев **нет**.
3. Комментарий **справа от SQL-выражения** — без ограничений по типу строки; остаётся на этой строке.
4. Несколько последовательных строк комментариев без пустых строк между ними образуют один комментарийный блок.

```sql
SELECT
    t.id -- Идентификатор
    -- Расчёт выручки
    , t.price * t.qty AS revenue
FROM products t

-- Учитываем только активные позиции
WHERE t.active = 1
```

### Неоднозначные комментарии

- Если комментарий на отдельной строке **отделён пустой строкой от следующего элемента или блока**, его принадлежность не угадывается.
- Такой участок сохраняется без изменений; остальная безопасная часть запроса форматируется.
- Выдаётся предупреждение с кодом, строкой и причиной.
- Комментарий без пустой строки перед следующим элементом считается относящимся к **следующему** элементу, даже если перед комментарием тоже нет пустой строки. Это согласованное исключение из идеи «симметрии».
- Содержимое комментариев не переписывается.

```sql
-- Неоднозначный случай
FROM users t

-- Неясно, к чему относится комментарий

INNER JOIN sales s
ON s.user_id = t.id
```

### Каналы вывода

- `stdout`: **только отформатированный SQL**.
- `stderr`: предупреждения (например, `SQLFMT-C001 | строка 5 | комментарий отделён от JOIN пустой строкой; участок не изменён`).
- Код завершения `0`, если безопасное форматирование завершилось, даже с предупреждениями.
- Фатальная ошибка — ненулевой код завершения; поведение DBeaver при получении `stderr` необходимо проверить на практике.
- Лог-файл — возможное дополнение, если DBeaver не показывает предупреждения; пока не обязательная часть контракта.

## 11. Операции над наборами и модификаторы SELECT

### UNION / UNION ALL / EXCEPT / INTERSECT

- Каждый оператор располагается **на отдельной строке**.
- **Ровно одна пустая строка до и после оператора**.
- Каждый `SELECT` форматируется по общим правилам, без изменения порядка операций и исходной группировки скобками.
- `ORDER BY`, относящийся ко всему составному запросу, не переносится внутрь отдельного `SELECT`.

```sql
SELECT
    id
FROM a

UNION ALL

SELECT
    id
FROM b

EXCEPT

SELECT
    id
FROM c
;
```

### Модификаторы и диалектные конструкции SELECT

- Модификаторы (`DISTINCT`, `ALL`, `TOP n` и другие распознанные парсером) остаются на строке заголовка `SELECT`; поля — ниже.
- **Порядок и написание модификаторов сохраняются**. Форматтер не исправляет синтаксис и не заменяет сокращения вроде `SEL` на `SELECT`.
- Распознавание структуры — по парсеру Teradata, а не по пробелам или регулярным выражениям.
- Если конструкцию нельзя безопасно распознать или преобразовать, действует правило предупреждения и сохранения участка без изменений.
- Общее правило UPPERCASE для SQL-ключевых слов не означает переписывание исходных сокращений, имён и литералов.

## 12. Безопасность и тестирование

Обязательные свойства:

- Идемпотентность: повторный прогон не меняет результат.
- Сохранение смысла SQL и исходных комментариев.
- Сохранение литералов, в том числе пробелов и переводов строк внутри них.
- Отдельные эталонные тесты для каждого правила и их сочетаний: комментарий + ведущая запятая, CTE + SELECT/FROM, JOIN/ON, WHERE/HAVING, QUALIFY + OVER, многоуровневая вложенность.
- Проверка, что `stdout` не загрязняется предупреждениями.
- Проверка нормализации нескольких вариантов произвольных пробелов, отступов и переносов в один и тот же результат.
- Неподдерживаемая, но распознанная конструкция: по возможности сохранить участок и предупредить. Нераспознанный SQL: не выдавать частично изменённый запрос как гарантированно корректный.

## 13. Зафиксированные решения по ранее открытым вопросам

1. **Смешанные `AND`/`OR` верхнего уровня:** не перестраивать выражение, предупреждать; без опасной вставки `1=1`.
2. **Регистр SQL-ключевых слов:** UPPERCASE. Не изменять написание идентификаторов, литералов и диалектных сокращений (см. §11).
3. **`UNION`, `UNION ALL`, `EXCEPT`, `INTERSECT`:** оператор на отдельной строке, одна пустая строка с обеих сторон (см. §11).
4. **Завершающий `;`:** отдельная строка.
5. **Многострочные `/* ... */` и комментарии между токенами:** текст комментария сохраняется; если невозможно безопасно определить границы форматирования, участок остаётся без изменений с предупреждением.
6. **`QUALIFY` со смешанными `AND`/`OR`:** сохранять исходную логическую группировку, не добавлять `1=1`; при неоднозначном преобразовании оставлять выражение без изменений с предупреждением.
7. **Модификаторы `SELECT`:** определяются парсером Teradata; сохраняются их порядок и написание; синтаксис не переписывается (см. §11).
