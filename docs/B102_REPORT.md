Ветка `feature/b10-stored-procedures`; merge/push не выполняются.

## B10.2a

- Единый `formatter_dialect.select_config` для runtime и CP01–CP05. Положительный
  выбор процедуры выполняется по lexer-токенам; литералы/комментарии не являются
  заголовками. Обычный SQL сохраняет штатный Teradata-диалект.
- Копия грамматики B10.1 получает проектный FluffConfig. Ни реестр диалектов,
  ни установленная SQLFluff не изменяются; карта смещений B6 сохранена.
- INSERT SELECT подключён к существующему узкому AST layout; граница INSERT/SELECT
  теперь явная. DELETE использует тот же безопасный обработчик WHERE, включая литералы.
- Исправлены воспроизводящие тесты B10.1: теперь они требуют идемпотентности INSERT
  и отсутствия E002 у DELETE, а не фиксируют известный дефект.
- На границе коммита a layout процедур намеренно ещё закрыт; DBeaver возвращает
  исходные байты. В b этот временный барьер заменяется транзакцией процедуры.

Целевые проверки: 20 tests / 0 FAIL / 0 ERROR. Полный предварительный прогон:
324 tests / 0 FAIL / 0 ERROR. После старта полного прогона в целевом наборе дополнительно
устранён конфликт двух whitespace-edits на границе многострочного INSERT/SELECT;
20 целевых тестов повторно прошли. Окончательный полный прогон после интеграции
проверит эту версию вместе с процедурами.

## B10.2b

- `formatter_procedure.py`: отдельный AST layout заголовка/параметров, BEGIN,
  DECLARE, SET, CALL, WHILE и вложенных блоков. Никакого regex-разбиения процедур.
- Вложенные INSERT/DELETE вызывают тот же существующий движок; его результат
  переносится узкими diff-edits и проверяется planner с protected spans. Комментарии
  и литералы не заменяются целиком. Все layout-edits имеют одну группу procedure.
- До layout выполняется B6-нормализация только вне protected spans; затем CP01–CP05
  и строгая валидация всего результата. Любой отказ возвращает весь исходник.
- В validator добавлены процедурные AST-контексты: оператор нельзя переместить в
  другой блок/цикл, удалить или изменить; допустимые case/prefix правила прежние.
- Новые golden/assertions проверяют точное оформление простой процедуры,
  вложенность DML, комментарии, многострочные protected значения и второй проход.
- 31 целевой тест прошёл, 0 FAIL / 0 ERROR. Полная транспортная проверка, BOM в
  CLI/адаптере и окончательный полный прогон выполняются в B10.2c.


## B10.2c — безопасность и транспорт

- BOM процедуры сохраняется при успехе и отказе через общий decode_sql_bytes для
  обоих CLI и адаптера. Для обычного SQL поведение B8/B9 не меняется.
- Политика B6 сохранена: LF вне protected spans; CR/LF/CRLF внутри строк,
  quoted identifiers и комментариев — точно исходные. При отказе возвращается
  исходная процедура целиком, включая BOM и все исходные окончания строк.
- Перед выдачей результата процедура проходит внутреннюю повторную проверку:
  второй результат должен быть побайтно идентичен первому и без диагностик отказа.
  Нестабильный вложенный DML приводит к полному откату, а не к частичному SQL.
- Именованные окна сохраняют E004; C001 для неоднозначных комментариев. Настоящие
  E001/E002 от planner сохраняются в диагностике, результат транзакции откатывается.
- Ошибки парсинга/валидации/case-pass/вложенного форматтера дают E003 и исходник.
  Текст исключений и SQL в диагностику не выводятся. Адаптер по-прежнему выдаёт
  только SQL даже при объединении stdout/stderr; GUI подменён только в тестах.
- Уточнено консервативное ограничение: комментарии внутри списка параметров
  процедуры или аргументов CALL → C001 и вся исходная процедура. Перенос запятой
  относительно такого комментария не выполняется без доказанной привязки.

## Пример input / actual / expected

Input:

```sql
replace procedure P(in D date) sql security invoker begin declare V date; set V=D; while V<D+2 do call LOG_P('DO; END --',V); set V=V+1; end while; end;
```

Actual первого прохода = expected нового golden = actual второго прохода:

```sql
REPLACE PROCEDURE p(
    IN d DATE
)
SQL SECURITY INVOKER
BEGIN
    DECLARE v DATE;

    SET v = d;

    WHILE v < d + 2 DO
        CALL log_p(
            'DO; END --'
            , v
        );

        SET v = v + 1;
    END WHILE;
END;
```

Для полной синтетической процедуры проверены DELETE, INSERT SELECT, INNER/LEFT JOIN,
CASE, вложенный SELECT, независимые WHERE, 3 DECLARE, 4 SET, CALL и WHILE.
SQL и результаты обоих проходов сохранены в артефакте matrix.json; вход — константа
SYNTHETIC в тесте B10.1. Диагностика успешных примеров на обоих проходах пуста.

результатов и списков диагностик идентичны. Покрыты SELECT, JOIN, GROUP/HAVING/ORDER,

разрешённое исправление и интеграцию, без удаления тестов.

## Ограничения и ручная приёмка

- Поддерживается ровно одна процедура из подмножества B10.1. IF/FOR/REPEAT,
  handlers/cursors, labels, UPDATE и самостоятельный SELECT внутри тела не добавлены.
  Несколько процедур в файле, неподдерживаемые атрибуты/SQL SECURITY также дают отказ.
- Распознавание — синтаксическое, не проверка существования объектов, типов или прав.
- Списки IN/выражения сохраняют действующие правила B8; новые стили длинных списков
  и устранение старых ограничений произвольных LF-переносов не реализовывались.
- Грамматика привязана к SQLFluff 4.4.0 и использует прежний изолированный config hook
  B10.1. Каталог prototypes/ теперь необходим при переносе проекта; инструкция
  Windows обновлена. Установленная библиотека не модифицирована, зависимостей нет.
- Реальная корпоративная процедура не предоставлена и не тестировалась. Все данные
  синтетические. Реальный Windows/DBeaver запуск не выполнялся; требуется ручная
  приёмка на ноутбуке, включая фокус GUI, таймаут и время больших процедур.
- CLI-аргументы и сигнатура format_sql не изменились; B9 selector и профили прежние.
  Master не меняется; push без отдельного согласования не выполняется.
