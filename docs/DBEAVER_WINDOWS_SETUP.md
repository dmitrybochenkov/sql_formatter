# DBeaver / Windows VDI — инструкция для ручной проверки B7

Статус: автоматизировано проверено на macOS, Python 3.12.8, SQLFluff 4.4.0.
Windows и DBeaver фактически не запускались. Совместимость на ноутбуке нужно
подтвердить по списку ниже. Архив B8 не планируется.

## Файлы и установка

Перенести проект, включая `.sqlfluff` (не потерять скрытый файл), `formatter.py`,
`formatter_modules/`, `prototypes/` (грамматика B10), `dbeaver_adapter.py`, `dbeaver_profile_selector.py`,
`dbeaver_formatter.py`, `requirements.txt`.
Для проверки также нужны `tests/` и `docs/`. Не переносить macOS venv / __pycache__.
SQLFluff требует Python >=3.10; кандидат для проверки — корпоративно разрешённый
Python 3.12 x64. Фактическую версию и архитектуру согласовать с IT. Сам форматтер
не использует сторонние пакеты кроме SQLFluff и его зависимостей.

Пример команд **cmd.exe** (заменить пути на реальные):

```bat
"C:\Python312\python.exe" -m venv "C:\Tools\SQL Formatter\.venv"
"C:\Tools\SQL Formatter\.venv\Scripts\python.exe" -m pip install -r "C:\Tools\SQL Formatter\requirements.txt"
"C:\Tools\SQL Formatter\.venv\Scripts\python.exe" -m pip check
```

Нужны разрешение на запуск Python/venv и права установки в выбранный каталог.
При отсутствии интернета подготовить wheels на разрешённой Windows-машине с
той же версией Python и архитектурой:

```bat
python -m pip download --only-binary=:all: -r requirements.txt -d wheelhouse
```

Перенести wheelhouse отдельно, затем выполнить на VDI:

```bat
"C:\Tools\SQL Formatter\.venv\Scripts\python.exe" -m pip install --no-index --find-links="C:\Tools\wheelhouse" -r "C:\Tools\SQL Formatter\requirements.txt"
```

Если wheel отсутствует, согласовать подготовку с IT, не устанавливать случайные
замены версий. requirements фиксирует SQLFluff, но не весь транзитивный граф;
сохранить `pip freeze` принятой Windows-установки для воспроизводимости.
После установки runtime не требует сети. Драйвер Teradata форматтеру не нужен.

## Настройка DBeaver

В Preferences найти SQL Editor → Formatting, выбрать External formatter.
Названия пунктов зависят от версии. Включить использование временного файла
(use temp file); stdin-режим адаптер не поддерживает. Кодировка SQL-редактора
должна быть **UTF-8**: DBeaver пишет временный файл и читает результат в кодировке
редактора. Команда — без shell, перенаправлений и активации venv:

```text
"C:\Tools\SQL Formatter\.venv\Scripts\python.exe" -B "C:\Tools\SQL Formatter\dbeaver_adapter.py" "${file}"
```

Выбрать `python.exe`, не `pythonw.exe`. Каждый путь и `${file}` заключить в кавычки.
Для B9 увеличить timeout, например до **120000 мс**: он включает время выбора
профиля и форматирования. Прежние 10000 мс могут истечь ещё до выбора.
Проверить единицы и поведение timeout в установленной версии DBeaver.
Форматирование: выделить SQL, Ctrl+Shift+F. Настройки quoting/timeout требуют
проверки в установленной версии DBeaver.

[Документация форматирования DBeaver](https://dbeaver.com/docs/dbeaver/SQL-Formatting/).
[Исследованный транспорт, закреплённая ревизия](https://github.com/dbeaver/dbeaver/blob/e97f23bcbd68db782b5300591dc4b61366f30c92/plugins/org.jkiss.dbeaver.model.sql/src/org/jkiss/dbeaver/model/sql/format/external/SQLFormatterExternal.java):
строки 104–131 — `${file}`, sourceEncoding, слияние stderr/stdout и использование
вывода даже при ненулевом коде завершения. Установленная версия может отличаться.

## Поведение адаптера

Один аргумент — файл. Исходные байты читаются до импорта форматтера. SQLFluff
конфигурируется проектным `.sqlfluff` относительно модуля, независимо от cwd/home.
Успех: UTF-8, LF вне protected spans; литералы/комментарии сохраняются.
Для процедур B10 исходный BOM сохраняется также при успехе; обычный SQL
сохраняет прежнее поведение B8/B9 (результат без BOM).
Валидатор вызывается явно и при наличии предупреждений. C001/E001/E002
записываются в журнал; безопасный проверенный результат может быть выдан.
E004/E003, неизвестная диагностика, неверная кодировка, исключение, ошибка
импорта/парсинга/валидации или неожиданный текстовый вывод: возврат исходных
байтов, включая BOM/CRLF/CR. Код 0 означает доставленный SQL, включая fallback,
а не обязательное успешное преобразование. Файл никогда не перезаписывается.

stdout содержит только SQL, stderr процесса адаптера заглушён. Python-потоки
при вызове форматтера перехватываются, файловые дескрипторы 1/2 перенаправлены
в null; итог выводится через сохранённый дескриптор. При импорте адаптера
перенаправления отсутствуют. Существующие CLI и format_sql не изменены.

Журнал: `%LOCALAPPDATA%\SQLFormatter\logs\adapter.jsonl`; если LOCALAPPDATA
не задана — подкаталог SQLFormatter/logs системного temp. Переменная окружения
`SQL_FORMATTER_LOG_DIR` задаёт другой каталог (DBeaver нужно перезапустить после
изменения его окружения). Успех без предупреждений не журналируется.
Около 256 KiB файл переносится в `adapter.previous.jsonl`, хранится один предыдущий
файл. Ротация best effort: при одновременных процессах возможна потеря записи,
это не влияет на SQL. Каталог должен быть доступен пользователю, с обычными
корпоративными ACL. Время UTC, код, тип и фиксированное описание — без SQL,
путей, traceback и текста исключения. Ошибка журнала игнорируется.

Коды ADAPTER-FORMAT: ошибка декодирования/импорта/форматирования/валидации
(поле type различает класс); REFUSAL: неподдерживаемая диагностика;
OUTPUT: неожиданный вывод; ARGS/READ/WRITE/START: ошибка соответствующего этапа.
Для C001/E002 часть изменений консервативно отклонена; E004 — именованное окно.

**Граница гарантий:** если исходный файл не удалось прочитать, вернуть его байты
невозможно; адаптер молча завершится с кодом 1 (аргументы: 2) без вывода. DBeaver
может заменить выделение пустой строкой. При недоступном/оборванном выходном
канале доставка SQL также невозможна; после частичной записи fallback не
дописывается. Ошибки до старта Python или синтаксическая порча самого адаптера
не контролируются им. Таймаут/убийство процесса со стороны DBeaver также вне
его контроля. Проверить эти случаи на копии SQL; не объявлять безусловную
защиту от любых сбоев редактора. Старый dbeaver_formatter.py напрямую к
External Formatter не подключать: его stderr DBeaver может вставить в SQL.

## Проверка установки

Сохранить test.sql в UTF-8:

```sql
SELECT id, name FROM users WHERE active=1;
```

В cmd.exe (не PowerShell с преобразованием кодировки перенаправленного вывода):

```bat
"C:\Tools\SQL Formatter\.venv\Scripts\python.exe" -B "C:\Tools\SQL Formatter\dbeaver_adapter.py" "C:\Tools\test.sql" > "C:\Tools\actual.sql"
```

Ожидается:

```sql
SELECT
    id
    , name
FROM users

WHERE active = 1
;
```

Полный тестовый набор из корня проекта:

```bat
.venv\Scripts\python.exe -B -m unittest discover -s tests -t . -p "test_*.py" -v
```

## Приёмка непосредственно на Windows / DBeaver

- Записать Windows/Python/DBeaver версии и архитектуру; проверить pip check.
- Проверить запуск из другой cwd, пути проекта/SQL/temp с пробелами и кириллицей.
- Проверить UTF-8, кириллицу, emoji, BOM и LF/CRLF/CR/mixed в protected spans.
- Повторно форматировать: побайтное равенство; исходный файл не меняется.
- Проверить SELECT FROM; и OVER w: исходный SQL сохранён, нет диагностики в редакторе.
- Проверить C001/E002, каталог журнала и запрет записи в него.
- Проверить стороннюю пользовательскую .sqlfluff и работу без сети.
- Проверить права на временный файл, отсутствие Python/зависимостей, timeout;
  подтвердить поведение редактора при пустом выводе до продуктивного подключения.
- Убедиться, что корпоративные AppLocker/EDR разрешают запуск, чтение temp,
  запись журнала; администраторские права и доступ к pip не предполагаются.

Отложенные ограничения произвольных LF-переносов B6 не исправлялись.


## B9: интерактивный выбор профиля

Команда External Formatter остаётся прежней: `python.exe -B dbeaver_adapter.py "${file}"`
(с полными путями и кавычками, как выше). Теперь после Ctrl+Shift+F открывается
окно SQL Formatter: `1` — Personal, `2` — Corporate, без Enter. Esc и крестик
возвращают исходные байты, включая BOM и окончания строк. Обе кнопки работают
мышью, если ОС не передала окну фокус. Неизвестные клавиши ничего не выбирают.
Автоматического выбора профиля при ошибке/отсутствии GUI нет.

Оба профиля используют один движок и одинаковые правила B8. Никаких различий
стиля пока нет. `formatter.py`, `dbeaver_formatter.py` и `format_sql` работают
без окна; GUI используется только точкой входа DBeaver-адаптера.

В базовой установке Python необходим Tcl/Tk. `tkinter` — стандартный модуль,
но в урезанной корпоративной поставке его может не быть. Не устанавливать
пакет tkinter через pip: проверить/включить Tcl/Tk в согласованной установке
Python. Ручная проверка на Windows: `.venv\Scripts\python.exe -m tkinter`.
Она должна открыть демонстрационное окно; [описание проверки в документации Python](https://docs.python.org/3.12/library/tkinter.html).
venv использует Tk своей базовой установки. Для переноса ZIP достаточно
включить новый `dbeaver_profile_selector.py` рядом с адаптером; новых сторонних
библиотек, плагинов DBeaver или дополнительных exe нет.

Новые коды журнала: ADAPTER-PROFILE (выбранный явный ID), ADAPTER-CANCEL
(отмена), ADAPTER-GUI (ошибка выбора/маршрутизации), ADAPTER-GUI-OUTPUT
(неожиданный вывод). Журнал по-прежнему не содержит SQL или текст исключений.
Ошибка журнала не препятствует возврату SQL.

На Windows отдельно проверить:

- Ctrl+Shift+F → 1 и → 2: одинаковый результат B8 и стабильный второй проход.
- Esc / крестик: SQL, включая BOM и окончания строк, сохранён.
- Фокус при старте, быстрый ввод, отключение topmost через 300 мс.
- Клик мышью при отказе ОС передать фокус, DPI и несколько мониторов.
- Отсутствие Tk, GUI-ошибка, E004, ошибка форматирования: в SQL нет диагностики.
- Долгое ожидание выбора и timeout DBeaver на копии запроса.

Окно не получает глобальные клавиатурные перехваты и не захватывает ввод других
приложений. Передача foreground-фокуса ограничивается политикой Windows/VDI,
поэтому она не гарантируется автоматическими headless-тестами. При убийстве
процесса по timeout возврат контролируется DBeaver, а не Python-адаптером;
сохраняются системные ограничения B7 для непрочитанного файла/оборванной трубы.


## B10.2: ручная приёмка процедур на Windows

Перенести **весь каталог prototypes/**: файл teradata_procedures.py теперь содержит
общую процедурную грамматику для runtime и CP01–CP05. Диагностический entry point
parse_procedure() сам в production не вызывается. SQLFluff должна быть ровно 4.4.0.
Новые зависимости и команды запуска не нужны.

Проверить Personal и Corporate на синтетической процедуре из
`tests/unit/test_procedure_prototype.py` (SYNTHETIC), затем на приватном исходном .sql
из редактора. Проверить второй Ctrl+Shift+F, отмену, BOM и Unicode, CRLF/CR внутри
литерала/comment, вложенные циклы и INSERT SELECT. Для IF/handler/cursor и другого
неподдерживаемого синтаксиса редактор должен получить всю процедуру без изменений.
Именованные окна сохраняют E004. Проверить журнал без содержимого SQL.

Процедура проверяется повторным внутренним проходом до выдачи результата;
время форматирования больших процедур может быть больше, чем обычного SELECT.
Измерить его на VDI и проверить таймаут DBeaver. Фактический Windows/DBeaver запуск
в B10.2 не выполнен. Реальная корпоративная процедура в репозиторий не включена.
