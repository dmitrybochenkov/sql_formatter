# Personal и Corporate

Personal необязателен. Без него работает встроенный Corporate, без диалогов и предупреждений. Программа не создаёт Personal автоматически. Python 3.11+ обязателен (`tomllib`); целевая версия — 3.12.

Чтобы включить личные настройки на Windows, без терминала:

1. В Проводнике откройте общий каталог проекта и `config_templates`.
2. Скопируйте `personal.example.toml`.
3. В адресной строке Проводника откройте `%LOCALAPPDATA%`, создайте папку `SQLFormatter`, если её ещё нет.
4. Вставьте копию и переименуйте её в `personal.toml` (включите отображение расширений файлов).
5. Откройте локальную копию текстовым редактором, измените параметры и сохраните как UTF-8.

Настройки применяются со следующего вызова DBeaver. Можно заменить локальный файл копией коллеги. Чтобы вернуться к Corporate, удалите локальный Personal. Удаление не вызывает предупреждения.

Единственные активные пути:

- Windows: `%LOCALAPPDATA%\SQLFormatter\personal.toml`.
- macOS: `~/Library/Application Support/SQLFormatter/personal.toml`.
- Linux: `$XDG_CONFIG_HOME/SQLFormatter/personal.toml`, если XDG_CONFIG_HOME абсолютный; иначе `~/.config/SQLFormatter/personal.toml` (правило XDG).

На Windows отсутствующий или относительный LOCALAPPDATA означает Corporate без поиска другого файла. На macOS/Linux LOCALAPPDATA не используется. Нет поиска в cwd, `.venv`, родительских каталогах, общей сетевой папке или корне проекта. Шаблон никогда не читается runtime; UNC-путь исходного кода не определяет путь настроек. Совместимость со старым корневым `personal.toml` намеренно отсутствует.

Corporate встроен в `formatter_modules/corporate_profile.py`, не читает Personal и изменяется разработчиком при выпуске. Это отсутствие штатных пользовательских overrides, а не защита исходного Python от намеренного редактирования. Оба профиля используют один движок и одинаковые обязательные проверки безопасности. Начальные Personal defaults зафиксированы отдельно; пропущенные необязательные поля берутся из них, а не из текущего Corporate.

## Параметры

| Раздел | Параметры | Значения |
|---|---|---|
| `case` | `keywords`, `functions`, `identifiers`, `types`, `literals` | `upper`, `lower`, `preserve` |
| `commas` | `select`, `from`, `group_by`, `order_by` | `leading`, `trailing` независимо |
| `spacing` | `blank_line_before` | список из `from`, `join`, `where`, `group_by`, `having`, `qualify`, `order_by`, без повторов; `[]` допустим |
| `where` | `insert_1_equals_1` | `true`, `false` |
| `group_by` | `layout` | `multiline`, `inline`, `preserve` |

`schema_version = 1` обязателен. Неизвестные параметры, неверные типы, значения, дубли ключей и ошибка TOML делают Personal невалидным; частичное применение настроек запрещено.

`preserve` регистра сохраняет написание исходных токенов. Для соответствующей категории CP-правило не запускается. Строки, комментарии и quoted identifiers защищены при любом регистре. `functions` распространяется и на UDF: SQLFluff не гарантирует различение UDF и встроенных функций. Новые служебные токены `AND` не имели исходного регистра: при `preserve` вставляются как `AND`; при `lower` нормализуются в `and`.

`leading` располагает запятую перед следующим элементом многострочного списка, `trailing` — после предыдущего. В однострочных списках разделитель всегда `, `. Аргументы функций, CALL, IN, VALUES и оконные PARTITION/ORDER не управляются этими настройками. Содержимое выражений и защищённых участков не переписывается.

`blank_line_before` задаёт одну дополнительную пустую строку на поддерживаемой AST-границе. Без включения в список блок начинается на следующей строке без дополнительной пустой. Привязанные комментарии сохраняются; неоднозначные границы не угадываются. Настройка `order_by` не касается ORDER BY внутри OVER.

`insert_1_equals_1 = false` запрещает добавление нового префикса WHERE; существующий не удаляется. `true` сохраняет прежнее ограничение: несколько непосредственных AND, без верхнеуровневого OR, с доказательством своей AST-области. AND внутри BETWEEN/скобок/подзапроса не учитывается как непосредственный. HAVING остаётся по прежним правилам; ON/QUALIFY не получают синтетический префикс.

GROUP BY:

- `multiline`: **один элемент всегда `GROUP BY a`**, независимо от исходного переноса. Два и более — построчно, с выбранными запятыми.
- `inline`: элементы на одной строке. Защищённые многострочные выражения и необходимые переносы вокруг комментариев сохраняются; комментарий не превращается в часть SQL и не поглощает следующий элемент.
- `preserve`: сохраняется наличие переноса после заголовка и между каждой парой элементов исходного AST. Число пустых строк и произвольный отступ не сохраняются. На переносимой границе применяется выбранная ведущая/завершающая запятая, на горизонтальной — `, `. Единственный элемент может оставаться под заголовком.

При неоднозначной принадлежности комментариев список консервативно сохраняется с C001, без частичного применения группы правок. Ошибки структуры/валидации сохраняют существующий rollback; для процедуры он атомарный целиком.

## Что появляется в DBeaver

- Personal отсутствует: Corporate без диалога и предупреждения.
- Валидный Personal совпадает с Corporate: форматирование Corporate без выбора.
- Валидный Personal отличается: окно Personal / Corporate; `1`/`2`, Esc/крестик — отмена. При ошибке окна выбора возвращается исходный SQL.
- Personal невалиден/недоступен: Corporate без выбора, понятное уведомление при первом обнаружении состояния; безопасная запись кода в журнал. GUI недоступен — состояние не помечается уведомлённым, Corporate остаётся доступен headless.

Сравниваются эффективные значения только пяти групп. Порядок ключей, комментарии, пробелы TOML и порядок списка `blank_line_before` не меняют стиль. Однако любое изменение байтов файла вызывает одно диагностическое уведомление: сначала диагностика, затем выбор (если нужен). Исправление ошибки и возврат к Corporate values также уведомляются. Первое обнаружение любого валидного файла с совпадающими эффективными значениями проходит без сообщения. Его хеш запоминается без GUI, чтобы последующие изменения обнаруживались. Удаление молча очищает запись о доставленном состоянии; повторное создание рассматривается как новый файл.

Состояние `profile_state.json` находится в том же локальном каталоге SQLFormatter. Оно содержит только версию, хеш содержимого, fingerprint Corporate и хеш пути локального Personal; пути общей установки не используются. Ни SQL, ни содержимое TOML, ни чувствительные пути не записываются. ОС-блокировка предотвращает параллельные уведомления; атомарная замена предотвращает частичный JSON. Занятый lock откладывает уведомление до следующего вызова. Если каталог недоступен, форматирование продолжается, но необходимые уведомления могут повторяться. Доставка сообщения записывается только после успешного показа; первый identical-state и удаление обслуживаются без сообщения. Отсутствие файла при отсутствии state не создаёт даже каталог. Обновление Corporate пересчитывает различия на каждом вызове.

## Технические границы

CLI `formatter.py [path]` остаётся headless, использует Corporate. Headless диагностика `tools/diagnose_formatter.py` сохраняет аргументы и умеет оба профиля. Официальная команда DBeaver не меняется. Ни GUI, ни настройки не пишутся в SQL stdout/stderr адаптера.

Runtime строит FluffConfig программно: Teradata/SQLFluff 4.4.0, raw, max_line_length=120, CP01–CP05 только. `.sqlfluff` остаётся историческим/ручным CLI-файлом и **не является источником runtime**. 120 — техническая настройка SQLFluff, не адаптивная ширина Python layout. Нет поиска cwd/home/inline настроек SQL. Один immutable snapshot распространяется на nested DML и повтор процедуры; request-local proofs разделяются по полному fingerprint настроек.
